# 如何維護這個開源專案

## 三層內容

- 手冊：編曲決策、記譜方式及驗收依據，放在 docs。
- 設定檔：團體或個人的字型、編制、基準八度、密度與交付偏好，放在 profiles。
- 工具：需求產生器、agent 文件建置，以及未來的節奏模型、MuseScore adapter 和渲染檢查。

## 第一版的範圍

已提供手冊、規則編號、agent 入口、可下載的 skill、需求 JSON／提示詞產生器，以及靜態網站建置。產生器只產生需求，不會自動轉錄音源或生成樂譜。

接下來先用另一首曲子完成一次端到端製譜。把跨作品仍成立的規則留下，把只對某首曲子有效的處理移入作品設定。優先建立原創四至八小節的回歸案例，再抽離音樂事件模型與 MuseScore adapter。

## 建議的工具介面

未來核心模型應區分 pitch、onset、duration、velocity、part 與視覺事件；Jianpu 的數字、點、橫線和減時線由語意事件產生，不靠逐首手寫座標。Adapter 負責讀寫 MuseScore，profile 負責外觀，檢查器驗證音樂不變與圖形間距。

轉譜、簡化、演奏改編與排版必須有各自的變更紀錄。對 layout-only 變更，核心音樂事件雜湊應一致。

## 不要把單機狀態當成標準

某次 MuseScore 轉檔崩潰、缺少 Qt 平台、不能多開視窗等，是 adapter 的已知環境限制。把檢查與能力偵測寫清楚，不要求所有人的電腦重現同樣操作，更不能把重設偏好或重裝當成預設修復。

## 貢獻與發布

修改規則請附規則編號與重現案例；更新手冊後重建網站和 agent bundle。每個發布版本可對應文件、profile 及測試結果，讓使用者可以固定某一版規則。

程式碼與手冊可公開，不表示歌曲、錄音、商用字型或他人的參考譜也可以一起公開。範例只使用原創或明確可再散布的素材。網站第一版不用帳號、不接收音訊或樂譜，上傳與自動生成服務是另外的產品階段。
